# Каркас MVC с активной моделью

Лабораторная работа №1, вариант 15 — «Генератор паролей».
Материал для пункта 4 задания («Разработать и описать в отчёте каркас MVC
с выданной по варианту моделью») и для контрольных вопросов 4 и 5.

---

## 1. Распределение обязанностей по слоям

| Слой | Классы | Обязанности | Чего слой НЕ делает |
|------|--------|-------------|---------------------|
| **Model** | `PasswordModel`, `PasswordGenerator`, `PasswordSettings`, `RawPasswordInput`, `IModelObserver` | Хранит состояние, проверяет данные, генерирует пароли, **сам оповещает представления** | Не знает о Qt Widgets, о классах представлений и о контроллере |
| **View** | `MainWindow`, `InputDialog` (+ формы `.ui`) | Отображает состояние, полученное от модели; собирает ввод; передаёт действия пользователя контроллеру | Не вычисляет, не проверяет данные, не хранит бизнес-состояние |
| **Controller** | `PasswordController` | Реагирует на действие пользователя: открывает окно ввода и передаёт «сырые» данные модели | **Не обновляет представление** и не проверяет данные |

Сборка всех трёх слоёв выполняется в одном месте — `src/main.cpp`
(composition root).

## 2. Почему модель активная

Различают две схемы MVC:

* **Пассивная модель** — модель не знает о представлениях. После изменения
  состояния **контроллер** сам вызывает методы представления, чтобы оно
  перерисовалось. Модель полностью пассивна: она только отвечает на запросы.

* **Активная модель** — модель хранит список подписчиков (представлений) и
  **сама рассылает им уведомления** при изменении состояния, ничего не зная
  об их конкретных классах. Контроллер после передачи данных в модель
  в обновлении экрана не участвует.

В проекте реализована **активная модель** (как требует вариант 15):

```cpp
// model/imodelobserver.h — интерфейс наблюдателя
class IModelObserver {
public:
    virtual ~IModelObserver() = default;
    virtual void onSettingsChanged(const PasswordSettings &settings) = 0;
    virtual void onPasswordsChanged(const QStringList &passwords)    = 0;
    virtual void onInputRejected(const QString &message)             = 0;
};
```

```cpp
// model/passwordmodel.cpp — модель сама оповещает подписчиков
void PasswordModel::submit(const RawPasswordInput &input)
{
    m_lastInput = input;                    // запомнили ввод

    PasswordSettings settings;
    QString error;
    if (!validate(input, settings, error)) {
        notifyInputRejected(error);         // ← оповещение от модели
        return;
    }

    m_settings  = settings;
    m_passwords = PasswordGenerator::generate(settings);
    m_hasResult = true;

    notifySettingsChanged();                // ← оповещение от модели
    notifyPasswordsChanged();               // ← оповещение от модели
}
```

```cpp
// controller/passwordcontroller.cpp — контроллер экран не трогает
void PasswordController::requestInput()
{
    InputDialog dialog(m_model.lastInput(), m_view);
    if (dialog.exec() != QDialog::Accepted)
        return;

    m_model.submit(dialog.rawInput());      // и всё: дальше работает модель
}
```

```cpp
// view/mainwindow.cpp — представление подписывается на модель
MainWindow::MainWindow(PasswordModel &model, PasswordController &controller, QWidget *parent)
    : QMainWindow(parent), ui(new Ui::MainWindow), m_model(model), m_controller(controller)
{
    ui->setupUi(this);
    m_model.attach(this);                                   // подписка
    connect(ui->buttonEnterData, &QPushButton::clicked,
            &m_controller, &PasswordController::requestInput);
    showInitialState();
}
```

Использован «ручной» паттерн Observer, а не сигналы Qt, чтобы:

1. слой Model не зависел от `QObject` и Qt Widgets и был пригоден
   для модульного тестирования без GUI;
2. механизм оповещения был виден в коде явно — это удобно защищать
   и показывать на диаграмме классов.

**Что нужно изменить, чтобы модель стала пассивной:** убрать из `PasswordModel`
методы `attach()/detach()/notify*()` и интерфейс `IModelObserver`; метод
`submit()` должен возвращать результат контроллеру, а контроллер — сам
вызывать методы `MainWindow` для обновления экрана.

## 3. Поток управления

```
                 нажатие «Ввести данные»
   Пользователь ─────────────────────────► MainWindow (View)
                                                │
                                                │ requestInput()
                                                ▼
                                        PasswordController
                                                │
                        InputDialog ◄───────────┤ открыть модальное окно,
                        (View)      ───────────►│ забрать RawPasswordInput
                                                │
                                                │ submit(rawInput)
                                                ▼
                                        PasswordModel (Model)
                                                │
                                                ├─ запомнить ввод
                                                ├─ validate()
                                                ├─ PasswordGenerator::generate()
                                                │
                                                │ onSettingsChanged()
                                                │ onPasswordsChanged()
                                                │ onInputRejected()
                                                ▼
                                        MainWindow (View)  ──► экран
```

Ключевая особенность: **обратная стрелка идёт из модели прямо в представление**,
минуя контроллер. Это и есть активная модель.

## 5. Проверки корректности ввода

Все проверки сосредоточены в `PasswordModel::validate()` — это бизнес-правила,
поэтому им место в модели, а не в форме:

| Ситуация | Сообщение |
|----------|-----------|
| Длина не указана | «Не указана длина пароля.» |
| Длина не число (`abc`) | «Длина пароля «abc» не является целым числом.» |
| Длина вне 4…128 | «Длина пароля должна быть в диапазоне от 4 до 128 символов (введено N).» |
| Количество не указано | «Не указано количество паролей.» |
| Количество не число | «Количество паролей «…» не является целым числом.» |
| Количество вне 1…50 | «Количество паролей должно быть в диапазоне от 1 до 50 (введено N).» |
| Не выбран ни один набор | «Не выбран ни один набор символов. Отметьте хотя бы один набор.» |
| Длина меньше числа наборов | «Длина пароля (N) меньше числа выбранных наборов символов (M)…» |

Поля длины и количества сделаны текстовыми (`QLineEdit`), а не счётчиками
(`QSpinBox`), намеренно: счётчик не дал бы ввести некорректное значение,
и продемонстрировать вывод сообщения об ошибке было бы нечем.

## 6. Ответы на контрольные вопросы

**1. Какие компоненты входят в состав IDE?**
Редактор кода с подсветкой синтаксиса и автодополнением; компилятор/интерпретатор
и система сборки; компоновщик; отладчик; средства навигации и рефакторинга;
менеджер проектов и зависимостей; интеграция с системой контроля версий;
средства визуального проектирования интерфейса (в Qt Creator — Qt Designer);
средства запуска тестов и профилирования; система расширений (плагинов).

**2. Каковы основные приёмы работы с редактором кода?**
Автодополнение (`Ctrl+Space`), переход к объявлению/определению (`F2`),
поиск использований, переименование-рефакторинг, сворачивание блоков, работа
с несколькими курсорами, быстрое переключение заголовок/реализация (`F4` в Qt
Creator), автоформатирование, закладки, поиск по проекту (`Ctrl+Shift+F`),
шаблоны кода (сниппеты).

**3. Каким образом выполняется сборка и запуск проекта?**
Проект описан в `CMakeLists.txt`. Qt Creator по выбранному комплекту (kit)
вызывает CMake, который генерирует файлы для Ninja; далее выполняются `moc`
(метаобъектный компилятор для классов с `Q_OBJECT`), `uic` (генерация
`ui_*.h` из форм `.ui`), компиляция `g++` и компоновка. Сборка — `Ctrl+B`,
запуск — `Ctrl+R`, запуск под отладчиком — `F5`.

**4. Что такое MVC?**
Архитектурный паттерн, разделяющий приложение на три слоя: Model (данные и
бизнес-логика), View (отображение) и Controller (обработка ввода пользователя).
Цель — снизить связанность: логику можно менять и тестировать независимо от
интерфейса, а интерфейс — заменять без переписывания логики.

**5. Чем отличается активная модель от пассивной?**
В **пассивной** модели модель не знает о представлениях; после изменения
состояния представление обновляет **контроллер**. В **активной** модели
модель хранит список подписчиков и **сама** рассылает им уведомления
(паттерн Observer), не зная о конкретных классах представлений; контроллер
в обновлении экрана не участвует. Активная модель удобнее, когда одно
состояние отображается несколькими представлениями или меняется не только
по действию пользователя.
