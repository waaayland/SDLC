# ADR-0002: Хранение данных в SQLite 3 (режим WAL), паттерн Repository и Unit of Work

## Контекст и постановка задачи

Согласно `CON-1`, `CON-3` и `REQ-INT-006`, все данные UAVLog хранятся локально в одном файле базы данных SQLite 3 без сетевого сервера. При этом операции регистрации полёта и ТО изменяют сразу несколько сущностей (запись полёта, налёт борта, состояние борта, счётчик циклов АКБ, журнал аудита) и обязаны быть строго атомарными даже при внезапном отключении питания ноутбука в полевых условиях (`REQ-REL-001`). Также требуется проверка целостности при запуске (`REQ-REL-003`), автоматическое резервирование раз в 24 часа с хранением 30 копий (`REQ-REL-002`) и фильтрация 20 000 записей за ≤ 1 с (`REQ-PERF-002`).

Как организовать доступ к SQLite 3, управление транзакциями и схему индексирования для гарантированной целостности и производительности?

## Драйверы решения

* **REQ-REL-001**: строгая атомарность операций при аварийном завершении или потере питания.
* **REQ-REL-002, REQ-REL-003, REQ-FUNC-015**: проверка целостности БД на старте, автоматическое и ручное резервирование.
* **REQ-PERF-001, REQ-PERF-002, REQ-PERF-003**: запуск ≤ 5 с, фильтрация ≤ 1 с, годовой отчёт ≤ 10 с на 20 000 полётах.
* **CON-3, CON-5**: один файл SQLite 3, только бесплатные компоненты.

## Рассмотренные варианты

* Вариант 1: SQLite 3 в режиме WAL + `PRAGMA foreign_keys = ON` + `PRAGMA synchronous = FULL` + паттерны Repository и Unit of Work (через `Qt6::Sql`)
* Вариант 2: SQLite 3 в режиме по умолчанию (`DELETE` journal) + прямые вызовы `QSqlTableModel`
* Вариант 3: Хранение данных в файлах JSON / XML с полной перезаписью при сохранении

## Итог решения

Выбранный вариант: **«SQLite 3 в режиме WAL + `PRAGMA foreign_keys = ON` + `PRAGMA synchronous = FULL` + паттерны Repository и Unit of Work»**, потому что режим WAL в сочетании с `synchronous=FULL` и явными транзакциями `BEGIN IMMEDIATE ... COMMIT` обеспечивает ACID-устойчивость при отключении питания (`REQ-REL-001`), ускоряет чтение/фильтрацию и позволяет безопасно выполнять горячее резервное копирование (`VACUUM INTO`), сохраняя простую переносимость файла (`REQ-INT-006`).

### Последствия

* Хорошо, потому что частичное сохранение полёта без пересчёта налёта и циклов АКБ невозможно физически (откат транзакции Unit of Work).
* Хорошо, потому что ссылочная целостность (`FOREIGN KEY`) и ограничения `CHECK` защищают данные даже при открытии БД внешним инструментом.
* Хорошо, потому что `VACUUM INTO` создаёт консистентную однофайловую резервную копию без остановки приложения и без артефактов `-wal`/`-shm`.
* Плохо, потому что во время работы рядом с `uavlog.db` временно существуют служебные файлы `-wal` и `-shm` — при ручном копировании пользователю нужно закрыть программу или использовать встроенную кнопку «Резервная копия» (при корректном закрытии выполняется `PRAGMA wal_checkpoint(TRUNCATE)`).

### Подтверждение

* Интеграционный тест отказоустойчивости (`REQ-REL-001`): 100 циклов записи с принудительным `TerminateProcess` и последующей проверкой `PRAGMA integrity_check` и инварианта «налёт == сумма полётов».
* Бенчмарк на эталонной БД (50 бортов, 20 000 полётов) проверяет выполнение запросов фильтрации с `EXPLAIN QUERY PLAN` (использование составных индексов, без `SCAN TABLE flights`).

## Плюсы и минусы вариантов

### SQLite 3 (WAL + FULL) + Repository / Unit of Work

Все SQL-запросы инкапсулированы в классах репозиториев инфраструктуры; транзакциями управляет `SqliteUnitOfWork`; при старте выполняется `PRAGMA quick_check` и миграции схемы по `PRAGMA user_version`.

* Хорошо, потому что полностью удовлетворяет `REQ-REL-001…003`, `REQ-PERF-001…003` и `REQ-MAINT-001`.
* Хорошо, потому что параметризованные запросы `QSqlQuery::bindValue` полностью исключают SQL-инъекции.
* Нейтрально, потому что требует ручного написания SQL-миграций при обновлении схемы.
* Плохо, потому что нужно контролировать выполнение `wal_checkpoint(TRUNCATE)` при выходе из программы.

### SQLite 3 (DELETE) + QSqlTableModel

Привязка таблиц БД напрямую к виджетам Qt.

* Хорошо, потому что быстрое прототипирование простых таблиц.
* Плохо, потому что жёстко связывает GUI со схемой БД, нарушая `REQ-MAINT-001`.
* Плохо, потому что сложнее гарантировать единую атомарную транзакцию сразу на 4 таблицы (`flights`, `uavs`, `batteries`, `audit_log`).

### Файлы JSON / XML

Сериализация всего парка и журналов в текстовые файлы.

* Хорошо, потому что человекочитаемый формат.
* Плохо, потому что нарушает `CON-3` (обязательный SQLite 3) и деградирует по памяти и скорости на 20 000 записях (`REQ-PERF-002`, `REQ-PERF-004`).
